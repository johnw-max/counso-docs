# Move a team from one use case to regular adoption

Start with one repeatable workflow to help the team build a routine. For a weekly support summary, members bring recent support conversations and issue notes into a shared workspace, an Agent produces a draft summary, and a reviewer turns the useful items into follow-up tasks.

## Choose and prepare the pilot

1. Name one decision the weekly summary should support, such as choosing which unresolved customer issues need an owner.
2. Select a small group of participants: one process owner, two or three regular users, and one reviewer who can judge accuracy.
3. Gather a representative week of permitted source material. Define the summary fields before the first run: issue, evidence, owner, next action, and a link or reference that the team can open.
4. Configure the Agent with the minimum sources and instructions needed for that decision. Keep the first run reviewable and avoid promising that it can change source systems by itself.
5. Put the output and follow-up tasks in a shared Pod or conversation that the pilot group can access.

## Teach the working pattern

Run a short live session around a real, non-sensitive example. Show how to ask for the summary, how to request a missing citation or a clearer owner, how to mark an item as a task, and how to correct an answer. Give participants a small practice request to complete on their own, then collect the questions that repeat.

Keep a one-page team recipe with the request wording, expected output fields, review owner, and escalation path. The recipe should explain what counts as evidence and when a person must verify the source before acting.

## Evaluate the trial

After two or three cycles, compare the result with the old process. Track completion time, the number of items needing rework, missing evidence, unassigned follow-ups, and whether the reviewer can make the same decision from the output. Ask each participant what they used, skipped, or had to repair.

Treat a failed run as input for an explicit change: narrow the source set, clarify an instruction, add a required output field, or change the review step. Re-run the same example and one new example after each change so improvement is visible.

## Expand with control

Expand when the pilot has a stable owner, a repeatable request, and an agreed quality check. Add one adjacent team or one adjacent source at a time. Publish the shared Agent or Skill only when its access scope and instructions match the larger audience, and give new users a short practice task before they rely on it for live work.

Review usage after expansion. Retire prompts that nobody uses, keep the evidence fields that help decisions, and route new use-case ideas through the same small trial instead of changing the shared workflow without a test.

## What success looks like

A new participant can run the recipe, recognize the required evidence, and route a follow-up without a pilot member sitting beside them. The process owner can explain what the Agent does, what the reviewer checks, and which source remains authoritative.

## Common questions

### How large should the first group be?

Use enough people to reveal different working habits while keeping review practical. Two or three regular users plus an owner and reviewer is a useful starting point.

### What if the summary is fluent but wrong?

Require evidence and a named reviewer in the output. Compare the claim with its source, then change the source scope or instruction and repeat the same test before expanding.

### When should we add another use case?

After the first workflow can be run and reviewed without special help. Keep the second use case as a separate pilot until its inputs, owner, and quality measure are clear.
